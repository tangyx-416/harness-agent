### Critical Security Finding: URL Redirection Vulnerability (FIXED)

**Vulnerability Discovered During Audit:**

Git configuration rules can redirect push destinations through:
- `url.*.insteadOf`
- `url.*.pushInsteadOf`
- `remote.*.pushurl`

An attacker with local Git config write access could redirect an approved `https://github.com/user/repo.git` push to `https://evil.example.com/repo.git` without the user seeing the actual destination in the approval prompt.

**Root Cause:**

Original policy used `git remote get-url origin` which returns the URL **after** `insteadOf` rewriting. The approval preview showed the rewritten URL, and the agent had no ground truth for comparison.

**Fix Implemented:**

Added `_reject_url_redirection()` in `src/harness_agent/git_remote/policy.py` that compares:
- Raw configured URL: `git config --get remote.<name>.url`
- Effective push URL: `git remote get-url --push <name>`

Any difference triggers rejection at prepare time with `RemotePushPolicyError`.

**Regression Tests Added:**
- `test_push_insteadof_redirect_rejected`
- `test_insteadof_redirect_rejected`
- `test_pushurl_redirect_rejected`
- `test_unrelated_insteadof_does_not_block_push`

**Status:** Fixed before release with comprehensive test coverage

## Implementation Overview

### New Agent-Visible Tools (2)

**Tool Count:** 22 total (+2 from v0.7.0)

1. `prepare_git_push(summary: str) -> dict`
   - Proposes push with zero network operations
   - Returns GitPushPlan with complete diff, commit list, destination URL
   - User approval required before any network operation

2. `get_git_push_result(plan_id: str) -> dict`
   - Checks push plan status
   - Returns pending/approved/applied/conflict/failed
   - Agent must wait for approval before claiming success

### Git Remote Policy

**Enforced at prepare time:**
- HTTPS-only URLs
- Current configured upstream only
- Existing remote branch only
- Clean working tree required
- At least one commit ahead
- No merge commits in outgoing range
- Bounded commit count (max 20)
- Bounded diff size (max 100KB)
- Fast-forward-only (behind/diverged rejected)
- URL redirection rejected

### Git Remote Service

**Three-phase protocol:**

1. **Preflight Read**
   ```bash
   git ls-remote <url> refs/heads/<branch>
   ```
   - Reads current remote OID
   - Compares against expected OID from plan
   - Mismatch → CONFLICT state, zero push attempts

2. **Lease-Bound Push**
   ```bash
   git push <url> refs/heads/<local>:refs/heads/<remote> \
     --force-with-lease=refs/heads/<remote>:<expected_oid> \
     -c core.hooksPath=/dev/null \
     -c gpg.program=false \
     -c push.followTags=false \
     -c push.recurseSubmodules=no
   ```
   - Exactly one attempt
   - CAS protection via --force-with-lease
   - Hooks/signers/tags/submodules suppressed

3. **Post-Push Verification**
   ```bash
   git ls-remote <url> refs/heads/<branch>
   ```
   - Reads remote OID after push
   - Must match approved HEAD exactly
   - Mismatch → FAILED state

### Session State Integration

**Four new events recorded:**
- `prepare_proposed` - Push plan created
- `prepare_approved` - User approved network operation
- `push_applied` - Remote branch updated successfully
- `push_conflict` / `push_failed` - Push rejected or failed

Events contain metadata only (no diffs, no credentials).

## Architecture

### Tool Authority Boundaries

| Operation | Agent | Policy | User | Host |
|-----------|-------|--------|------|------|
| Propose push | YES | - | - | - |
| Validate plan | - | YES | - | - |
| Approve network | - | - | YES | - |
| Execute push | - | - | - | YES |
| Verify remote | - | - | - | YES |

### Data Flow

```
Agent calls prepare_git_push(summary)
  ↓
Policy: validate_and_prepare_push()
  - Read local Git state (zero network)
  - Validate URL (HTTPS-only, redirection check)
  - Validate branch (upstream configured, ahead)
  - Validate commits (fast-forward, no merges)
  - Generate complete diff
  ↓
Create immutable GitPushPlan
  ↓
Register with GitRemoteBroker (pending state)
  ↓
Return plan to agent
  ↓
Agent calls get_git_push_result(plan_id) → "pending"
  ↓
Agent stops (cannot claim push success)
  ↓
Host presents approval prompt to user
  - Destination URL
  - Outgoing commits
  - Complete unified diff
  ↓
User approves or rejects
  ↓
If approved:
  Broker: pending → approved
  Host: take_for_apply() → approved → applying
  Service: apply_push()
    - Preflight ls-remote
    - If conflict: CONFLICT state, return
    - Execute push once
    - Post-push ls-remote
    - If mismatch: FAILED state
    - If match: APPLIED state
  Broker: record result
  ↓
Next turn: Agent calls get_git_push_result(plan_id)
  ↓
Returns "applied" with remote OID
  ↓
Agent can now claim remote success
```

## Limitations (By Design)

v0.8.0 Git remote push has intentional constraints for safety:

1. **HTTPS only** - No SSH, file://, git@, or other schemes supported
2. **Current configured upstream only** - No arbitrary remote/branch selection
3. **Existing remote branch only** - No branch creation or deletion
4. **Fast-forward only** - No force-push authority; behind/diverged rejected
5. **No tags** - Branch-only push (tags suppressed even with push.followTags=true)
6. **No remote deletion** - No ref deletion capability
7. **No fetch/pull** - Push-only capability, no automatic sync
8. **No automatic retry** - Single network write attempt on any failure
9. **Local commit ≠ remote success** - Agent must verify with get_git_push_result

These are deliberate safety boundaries, not bugs or incomplete features.
