## J. Stage Service

### Revalidation

When `apply_stage_plan()` is called on an already-applied plan:
- The service re-validates the current Git state against the approved snapshot
- If the state changed, it returns `GitMutationResult` with status `CONFLICT`
- If the state is unchanged, it returns the cached `APPLIED` result
- No duplicate application occurs

**Test:** `test_stage_apply_exactly_once_sequential`

### Compensation

If `apply_stage_plan()` detects a conflict (stale HEAD, branch, worktree, or index):
- Returns `GitMutationResult` with status `CONFLICT` and detailed message
- Performs **zero** index mutation
- The user is informed and must re-prepare with current state

**Tests:**
- `test_stage_apply_detects_head_changed`
- `test_stage_apply_detects_branch_changed`
- `test_stage_apply_detects_worktree_changed`
- `test_stage_apply_detects_index_changed`

### Exactly-Once

**Sequential:** Multiple calls to `apply_stage_plan()` with the same plan return the cached result. Only the first successful application mutates the index.

**Concurrent:** Multiple threads compete via `broker.take_for_apply()`. Only one thread successfully claims the plan and records the result. Other threads receive failure from the broker.

**Tests:**
- `test_stage_apply_exactly_once_sequential`
- `test_stage_apply_concurrent_exactly_once`
