## D. GitFetchPlan / GitFetchResult

**GitFetchPlan (Immutable):**
- `plan_id` - Unique plan identifier
- `kind` - Always "fetch"
- `summary` - User-provided description
- `local_branch` - Current branch name
- `local_head_oid` - Current HEAD commit
- `remote_name` - Remote name (e.g., "origin")
- `remote_branch` - Remote branch name
- `tracking_ref` - Full ref path (e.g., "refs/remotes/origin/main")
- `expected_tracking_oid` - Current tracking ref OID
- `approved_remote_url` - HTTPS URL only
- `remote_host` - Hostname extracted from URL
- `created_at` - Timestamp

**GitFetchResult (Immutable):**
- `plan_id` - Matches plan
- `state` - FetchState enum (applied/conflict/failed)
- `remote_name`, `remote_branch`, `tracking_ref` - From plan
- `previous_tracking_oid` - Before fetch
- `observed_remote_oid` - Fetched remote commit
- `updated_tracking_oid` - After tracking ref update
- `changed` - Boolean indicating if ref was updated
- `message` - Human-readable status
- `created_at` - Timestamp

## E. GitFetchBroker State Machine

States:
1. **PENDING** - Plan registered, awaiting user approval
2. **APPROVED** - User approved, ready for application
3. **APPLYING** - Host is executing fetch
4. **APPLIED** - Fetch completed successfully
5. **REJECTED** - User rejected the plan
6. **CONFLICT** - Non-fast-forward or state changed
7. **FAILED** - Network or Git error

**Atomic Operations:**
- `take_for_apply()` - Ensures exactly-once execution under lock
- Multiple concurrent callers: exactly one succeeds

## I. HTTPS URL Policy

**Production v0.9 supports HTTPS ONLY.**

**ACCEPT:**
- `https://github.com/example/repo.git`

**REJECT:**
- `http://` (insecure)
- `ssh://` or `git@host:path`
- `git://`
- `file://`
- `ext::`
- Local paths
- UNC paths
- Embedded credentials
- Query strings
- Fragments

## J. URL Rewrite / Destination Security

v0.9 applies the same URL redirection defense as v0.8 push:

**Security Check:**
Compare raw configured URL vs. effective fetch URL that Git resolves.

**Reject if:**
- `url.*.insteadOf` would rewrite the destination
- Raw URL ≠ Effective URL

**Core Invariant:**
```
APPROVED FETCH DESTINATION == GIT FETCH DESTINATION
```

This prevents:
```
User approves: https://github.com/example/repo.git
Git fetches:   https://attacker.com/evil.git  ← BLOCKED
```

## M. Apply-Time Revalidation

Before network access, revalidate:
- Current branch unchanged
- HEAD unchanged
- Upstream configuration unchanged
- Remote URL unchanged
- Tracking ref unchanged
- Tracking OID == expected_tracking_oid

**If any changed:** CONFLICT, ZERO network operation.

## N. Exact Fetch Command Construction

**Host-generated fixed argv:**
```bash
git fetch \
  --no-tags \
  --no-recurse-submodules \
  --no-write-fetch-head \
  -c fetch.recurseSubmodules=false \
  -c submodule.recurse=false \
  <approved-https-url> \
  refs/heads/<remote-branch>:refs/harness-agent/fetch/<plan-id>
```

**Requirements:**
- shell=False
- Fixed git executable
- Exact approved HTTPS URL
- One exact source branch
- Isolated temporary destination ref
- No wildcard refspec
- No tags
- No submodules
- No automatic maintenance

**Not Used:**
- `git fetch origin` (uses configured refspecs)
- `git fetch --all`
- `git pull`
- `git remote update`

## O. Temporary Harness Ref Design

**Isolated namespace:** `refs/harness-agent/fetch/<plan-id>`

**Properties:**
- Unique per plan
- Never model-selected
- Never collides with user refs
- Deleted after terminal processing
- Not part of agent-visible Git surface

**Flow:**
1. Fetch into `refs/harness-agent/fetch/<plan-id>`
2. Resolve and validate fetched commit
3. Check fast-forward relationship
4. Atomic CAS update of tracking ref
5. Cleanup temporary ref

## P. Fast-Forward Tracking Policy

Let A = expected_tracking_oid, B = observed_remote_oid

**Cases:**
- `A == B` → No-op, tracking unchanged, APPLIED
- `A ancestor of B` → Fast-forward, update tracking A→B, APPLIED
- `B ancestor of A` → Remote moved backwards, CONFLICT
- `A and B diverged` → Histories diverged, CONFLICT
- `Unrelated history` → CONFLICT

**v0.9 does NOT silently accept remote force-push / history rewrites.**

## Q. Tracking-Ref CAS

**Atomic compare-and-swap:**
```bash
git update-ref <tracking-ref> <new> <expected-old>
```

If tracking ref changes concurrently before update:
- CAS fails
- Result: CONFLICT
- No retry
- No overwrite of concurrent change

**Core Invariant:**
```
EXPECTED TRACKING REF == ONLY TRACKING REF MUTATED
```

## W. Exactly-Once Network Authority

**Broker lifecycle states:**
```
pending → approved → applying → applied
pending → rejected
approved → applying → conflict/failed
```

**`take_for_apply()` is atomic under lock.**

20 concurrent callers → exactly ONE obtains authority.

**One user approval permits at most ONE fetch network attempt.**

No automatic retry on:
- Authentication failure → FAILED
- Network failure → FAILED
- Remote branch missing → CONFLICT/FAILED
- Tracking CAS race → CONFLICT
- Remote history rewrite → CONFLICT

## AJ. Limitations

v0.9.0 explicitly **does NOT** provide:

1. **Working tree/index mutation** - Fetch only updates tracking refs
2. **Pull/merge/rebase** - User must separately merge if desired
3. **Arbitrary remote selection** - Only configured upstream
4. **Tag fetching** - Tags explicitly suppressed
5. **Submodule recursion** - Submodules explicitly suppressed
6. **Remote branch creation** - Only existing tracking refs
7. **Force-fetch** - Non-fast-forward updates rejected
8. **Automatic retry** - One approval = one attempt max
9. **SSH/Git protocol** - HTTPS only
10. **DNS/proxy control** - OS-level routing unchanged

**Documented limitations that v0.9 does NOT claim to control:**
- DNS resolution (OS-level)
- HTTP proxies (OS/Git config)
- Server-side behavior
- Physical network routing

**Guarantees are about:**
- Approved Git URL/ref scope
- Host-generated command scope
- Bounded local ref mutation
- No working-tree/index/local-branch mutation
- No remote mutation by Harness fetch

## AL. Implementation Decisions

**Key architectural choices:**

1. **Separate GitFetchBroker** - Not reusing GitRemoteBroker because push and fetch are distinct authorities
2. **Isolated temporary ref** - Using `refs/harness-agent/fetch/<plan-id>` prevents collision with user refs
3. **Fast-forward-only** - Rejecting non-fast-forward updates preserves safety
4. **HTTPS-only production** - Simplifies security model, no SSH key management
5. **Zero-network prepare** - Allows safe proposal without touching network
6. **Atomic CAS update** - Prevents race conditions with concurrent fetches
7. **No automatic retry** - One approval = one attempt, forcing explicit re-approval
8. **Working tree preservation** - Fetch doesn't touch user's current work
